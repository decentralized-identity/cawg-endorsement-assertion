An _ODRL Permissions Assertion_ is a C2PA assertion that encodes permissions using the Open Digital Rights Language (ODRL) standard. This specification replaces the previous Endorsement Assertion with a standards-based approach that provides better interoperability, clearer semantics, and enhanced validation capabilities for permissions in C2PA manifests.

== Introduction

_This section is non-normative._

=== Overview

The ODRL Permissions Assertion system establishes a standards-based permissions framework for C2PA that enables:

1. **ODRL-based permissions** - Standards-compliant permission encoding using ODRL 2.2
2. **CAWG Identity binding** - Cryptographic binding to CAWG Identity assertions
3. **C2PA integration** - Seamless integration with C2PA manifest validation
4. **Interoperability** - Compatible with JPEG Trust and other ODRL implementations

This system provides a robust permission mechanism where content creators can grant machine-readable rights using established web standards while maintaining cryptographic proof of identity and authority.

=== Use case

As one example, a content creator may want to grant permission to a content-distribution network to transcode their C2PA asset as part of a publication workflow. The creator issues an ODRL Offer that identifies the licensee, references their CAWG Identity assertion for identity assurance, and includes ODRL policies that define the scope, duration, and terms of the permission. When the transcoder creates their C2PA asset containing the ingredient, they include the ODRL Agreement as a *permissions assertion,* which lets the C2PA Manifest consumer know that the actions they performed have been properly authorized.

== Terms and definitions

=== Actor

A human or non-human (hardware or software) that is participating in the C2PA ecosystem. For example: a camera (capture device), image editing software, cloud service, or the person using such tools.

NOTE: An organization or group of _actors_ may also be considered an _actor._

=== C2PA asset

A file or stream of data containing _digital content,_ _asset metadata,_ and a _<<C2PA Manifest>>_.

For the purposes of this definition, we will extend the typical definition of "file" to include cloud-native and dynamically-generated data.

IMPORTANT: The definition of "C2PA asset" in this specification differs from the definition of "asset" given in the C2PA technical specification. A "C2PA asset" as defined in _this_ specification MUST contain a _<<C2PA Manifest>>._

=== C2PA Manifest

The set of information about the _provenance_ of a _<<C2PA asset>>_ based on the combination of one or more assertions, a single C2PA claim, and a claim signature.

See link:++https://c2pa.org/specifications/specifications/2.0/specs/C2PA_Specification.html#_manifests++[Section 11, "Manifests,"] of the C2PA technical specification.

=== ODRL Permissions Assertion

A C2PA assertion that contains an ODRL policy (Offer or Agreement) encoded as JSON-LD, following the CAWG ODRL Profile for C2PA.

=== CAWG ODRL Profile

A specific profile of ODRL 2.2 that defines the constraints and extensions needed to use ODRL within C2PA manifests, identified by the IRI `https://cawg.io/profiles/odrl-c2pa/v1`.

=== Assigner

An _<<_actor,actor>>_ who grants permissions in an ODRL policy (equivalent to _licensor_ in traditional licensing).

=== Assignee

An _<<_actor,actor>>_ who receives permissions in an ODRL policy (equivalent to _licensee_ in traditional licensing).

=== CAWG Identity Assertion

A C2PA assertion that provides identity verification for the assigner and assignee in ODRL policies.

== CAWG ODRL Profile for C2PA

The CAWG ODRL Profile for C2PA defines the specific constraints and extensions needed to use ODRL within C2PA manifests. See xref:_profile[xrefstyle=full] for complete details.

=== Profile IRI

The CAWG ODRL Profile is identified by the IRI:

----
https://cawg.io/profiles/odrl-c2pa/v1
----

=== Key Features

* **Pure ODRL**: Uses standard ODRL 2.2 classes and properties
* **C2PA Binding**: Extends ODRL with C2PA-specific linking mechanisms
* **Identity Verification**: Cryptographic binding to CAWG Identity assertions
* **Atomic Policies**: Enforces ODRL atomic policy requirements
* **Conflict Resolution**: Default conflict strategy of `invalid`

=== Allowed Actions

The profile restricts ODRL actions to the following C2PA-safe values:

* `c2pa.published` - Permission to publish the asset
* `c2pa.transcoded` - Permission to transcode the asset  
* `c2pa.repackaged` - Permission to repackage the asset

== Identity Binding

=== CAWG Identity Assertion Requirement

The `assigner` and `assignee` in ODRL policies MUST be verifiable via a CAWG Identity assertion in the same manifest. The `cawg:assertionRef` property MUST point to that CAWG Identity assertion using a JUMBF self-link.

=== Cryptographic Verification

Validators MUST check cryptographic continuity between the CAWG Identity assertion and the signer of the relevant claim (assigner/assignee roles). This ensures that the identities in the ODRL policy are cryptographically bound to the manifest signer.

== Target Binding

=== Ingredient Reference

The policy's `target` MUST reference the asset via JUMBF or via `cawg:ingredient` that resolves to the single `c2pa.ingredient` referenced by `c2pa.actions`.

=== Atomic Requirements

Following ODRL specification §2.7, policies MUST be expanded into atomic rules where each permission targets exactly one Asset.

== Offer → Agreement Path (Countersign)

=== Offer Phase

An _<<_assigner,assigner>>_ publishes an ODRL Offer containing the terms and conditions for permission to use their C2PA asset. The Offer includes:

* `@type`: `Offer`
* `assigner`: The licensor's identity
* `permission`: Array of permitted actions and constraints
* `cawg:assertionRef`: Reference to CAWG Identity assertion
* `cawg:ingredient`: Reference to the ingredient assertion

=== Agreement Phase

A _<<_assignee,assignee>>_ accepts the Offer by including an ODRL Agreement in an update manifest. The Agreement includes:

* `@type`: `Agreement`
* `assignee`: The licensee's identity (bound to their CAWG Identity assertion)
* `inheritFrom`: Reference to the original Offer's `uid`
* Same `permission` structure as the Offer
* Optional `obligation` for additional duties

=== Validation Requirements

Validators MUST regard an Agreement that inherits or restates the Offer with the same `uid` (or `inheritFrom`) as acceptance of the original Offer terms.

== Validation Algorithm

The validation algorithm for ODRL Permissions Assertions follows these normative steps. See xref:_validation[xrefstyle=full] for complete details.

=== Preconditions

The validator MUST ensure the following preconditions are met:

1. Exactly one `c2pa.actions` assertion exists in the manifest
2. Exactly one relevant `c2pa.ingredient` assertion exists and is linked
3. One ODRL policy assertion per policy being evaluated
4. All required CAWG Identity assertions are present

=== Validation Steps

1. **Atomic Expansion**: Expand compact ODRL policies into atomic rules
2. **Profile Validation**: Check profile matches CAWG ODRL profile IRI
3. **Identity Binding**: Verify assigner/assignee against CAWG Identity assertion
4. **Target Binding**: Verify ingredient binding via JUMBF references
5. **Constraint Evaluation**: Evaluate all constraints (date, territory, etc.)
6. **Obligation Evaluation**: Evaluate machine-checkable obligations only
7. **Conflict Resolution**: Apply conflict strategy (default: `invalid`)
8. **Status Attestation**: Handle optional status attestations

=== Result Classification

The validator MUST return one of:
* `valid` - All checks pass
* `valid-with-nonverifiable-obligations` - Valid but has non-machine-checkable obligations
* `invalid` - One or more checks fail
* `indeterminate` - Cannot determine validity due to missing information

== Interoperability with JPEG Trust

This profile uses vanilla ODRL and JSON-LD, making it compatible with JPEG Trust guidance. The CAWG ODRL Profile adds the missing identity/target/validation specifics needed for C2PA integration while maintaining full ODRL compliance.

=== Key Interoperability Features

* **Standard ODRL**: Uses ODRL 2.2 classes and properties without modification
* **JSON-LD Context**: Extends ODRL context with C2PA-specific terms
* **Profile-based**: Uses ODRL profile mechanism for C2PA constraints
* **Reference Compatibility**: Can be referenced by CAWG Identity per JPEG Trust guidance

== Migration from Endorsement

See xref:_migration[xrefstyle=full] for guidance on migrating from the previous Endorsement Assertion to ODRL Permissions Assertion.

=== Key Changes

* **Structure**: Flat endorsement structure → Hierarchical ODRL structure
* **Identity**: COSE signature → Manifest signature + CAWG Identity assertion
* **Validity**: Direct date fields → ODRL constraints
* **Actions**: `c2pa.actions` array → `action` within `permission` array

== Examples

=== Minimal Offer

[source,json]
----
{
  "@context": [
    "https://www.w3.org/ns/odrl.jsonld",
    "https://cawg.io/contexts/odrl-c2pa/v1"
  ],
  "@type": "Offer",
  "uid": "urn:uuid:odrl-offer-123",
  "profile": "https://cawg.io/profiles/odrl-c2pa/v1",
  "assigner": "did:web:originvault.io",
  "permission": [{
    "target": "self#jumbf=c2pa/…/c2pa.assertions/c2pa.ingredient",
    "action": "c2pa.transcoded",
    "constraint": [{
      "leftOperand": "odrl:dateTime",
      "operator": "odrl:lteq",
      "rightOperand": "2026-12-31T23:59:59Z"
    }]
  }],
  "cawg:assertionRef": "self#jumbf=c2pa/…/c2pa.assertions/cawg.identity",
  "cawg:ingredient": "self#jumbf=c2pa/…/c2pa.assertions/c2pa.ingredient"
}
----

  "uid": "urn:uuid:odrl-agreement-456",
  "inheritFrom": "urn:uuid:odrl-offer-123",

  "assigner": "did:web:originvault.io",
  "assignee": "did:web:licensee.example",

    "action": "odrl:attribute",

}
